# Envelope v1

The normative wire schema is [`om/sanchar/v1/envelope.proto`](om/sanchar/v1/envelope.proto). This page defines the v0.1 behavior that Protobuf field types alone cannot express.

- `version` must be the integer `1`. The separate package path `om.sanchar.v1` identifies the schema compatibility line.
- `id` is a 26-character uppercase Crockford Base32 ULID. Its first character is `0` through `7`; `I`, `L`, `O`, and `U` are excluded.
- `idempotency_key` contains 1–128 UTF-8 bytes. In the stream protocol, its dedupe scope is one stream. Broader request-side dedupe scope is an open question.
- `from` and `to` are canonical addresses as defined in `address.md`. The gateway authenticates the sender independently; an address is not an identity proof.
- `kind` is one of `REQUEST`, `RESPONSE`, `EVENT`, or `CONTROL`. `UNSPECIFIED` is invalid for a processed envelope.
- `payload` is opaque to the envelope. Each protocol binding defines its payload encoding. In public Protobuf JSON, `payload`, `grant`, and `signature` use base64 strings.
- In public Protobuf JSON, 64-bit integer fields serialize as decimal strings; parsers may accept JSON integer numbers as permitted by Protobuf JSON, but must reject booleans, fractions, and out-of-range values.
- `meta.tenant` uses the canonical tenant syntax from `address.md`. It selects the policy, quota, residency, and metering context; the gateway must authorize its use.
- `meta.class` must be `VOICE`, `INTERACTIVE`, or `BATCH`. `UNSPECIFIED` is invalid for a processed envelope.
- `meta.deadline_ms` is a relative remaining duration in milliseconds, not a wall-clock timestamp. Zero means that the ingress hop must use the configured policy deadline; a forwarded request must carry a positive remaining duration. Each hop creates an internal monotonic deadline. Before forwarding, it subtracts elapsed local monotonic time (rounded up to a whole millisecond) and the configured per-hop safety margin. The remaining value must meet the configured minimum useful downstream duration; otherwise the hop fails fast with `OS-0500`. Clock skew between hosts must not affect deadline enforcement.
- Absent budget limits inherit configured policy ceilings; explicit zero means no spend or token budget. `cost_limit_microcredits` is an optional signed 64-bit integer constrained to `[0, 2^63-1]`; negative values are invalid. One microcredit is the platform's integer accounting unit.
- `seq` is per stream, begins at 1, and zero means not assigned. A receiver must reject regressions or gaps unless the stream protocol explicitly permits them.
- `grant` is opaque in v1 and must be verified against the applicable identity/policy profile. `signature` may be present, but the signing algorithm/profile is not selected by this draft.

The executable structural validator and JSON conformance vectors are under `spec/reference` and `spec/conformance`. The validator is a reference, not a security boundary for production code.

## Deadline and spend enforcement

The tenant policy must define a positive maximum deadline, a non-negative per-hop safety margin, and a positive minimum useful downstream duration. At ingress, `deadline_ms == 0` selects the maximum; a positive caller value is capped at it. Each hop starts a local monotonic timer from the received duration. Before forwarding, it computes `received_duration - ceil(elapsed_monotonic_ms) - safety_margin_ms`. It fails with `OS-0500` when this result is below the configured minimum useful duration; otherwise it forwards that result and uses it as the outbound transport timeout. The receiver starts its own monotonic timer from the smaller forwarded duration. No hop compares the field with a wall clock or adds clock-skew compensation. Transit time is not encoded; the safety margin reserves time for network transit and variance, and the margin is consumed at every hop. The transport must propagate cancellation when the local outbound timeout expires.

Spend limits are evaluated against a versioned price-table snapshot selected for the authorized tenant and route at admission. A table entry identifies the billable metric and gives a non-negative `uint64` `microcredits_numerator` and positive `uint64` `units_denominator`; its rate is that rational number of microcredits per unit. Cumulative usage and both rate fields are unsigned 64-bit integers. For each metric, charge is `ceil(cumulative_units * numerator / denominator)`. The marginal charge for newly observed usage is the new cumulative charge minus the previously assessed cumulative charge, so provider chunk boundaries cannot change the total. Products are evaluated exactly in `uint128` and ceiling division is computed without an overflowing addition. Per-metric charges and their sum must fit a non-negative signed 64-bit microcredit amount; otherwise the request is rejected as `OS-0201`, never wrapped.

The gateway reserves/assesses each marginal charge before releasing the corresponding billable output. It releases an output only when the resulting cumulative charge is at most the authorized limit. If the next output would exceed the limit, it is withheld and the stream ends with core cause `OS-0201`; if the output exactly consumes the remaining balance, it is released and the stream then ends before another billable output is released or requested upstream. An HTTP 429 binding may serialize this as public code `OS-3029` and must preserve `cause: OS-0201`; a rolling tenant quota instead uses `cause: OS-0200`. A zero spend limit is checked before contacting the upstream. The price-table version and assessed usage are attached to the metering record so a later table update cannot reprice an in-flight request.
